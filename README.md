# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 2차원 패턴이 어떤 필터에 더 가까운지 판별하는 Python 콘솔 애플리케이션입니다. 사람이 직관적으로 '십자가(Cross)'와 'X'를 구분하듯, 컴퓨터에게 두 패턴을 숫자 배열로 표현해 위치별 곱셈·합산(MAC) 점수를 계산하고 그 결과로 라벨을 결정합니다.

본 프로젝트는 미니 NPU의 핵심 연산을 손으로 구현하는 학습용으로, **외부 라이브러리 없이 Python 표준 라이브러리만** 사용합니다. NumPy 같은 벡터화 라이브러리는 사용하지 않으며, MAC 연산은 이중 for-loop으로 직접 구현합니다.

## 1. 실행 방법

### 요구 환경

- Python 3.8 이상 (외부 라이브러리 불필요)
- macOS / Linux / Windows 어디서든 동일하게 동작

### 실행

```bash
python main.py
```

실행하면 모드 선택 메뉴가 표시됩니다.

```text
=== Mini NPU Simulator ===

[모드 선택]

1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **모드 1**: 사용자가 직접 3×3 필터 두 개와 패턴 한 개를 입력합니다.
- **모드 2**: 프로젝트 루트의 `data.json`을 읽어 5×5/13×13/25×25 케이스를 일괄 분석합니다.

`data.json`은 프로젝트 루트(`main.py`와 같은 위치)에 있어야 합니다.

### 모드 1 입력 형식 예시

각 행은 공백으로 구분된 숫자 3개, 총 3줄을 입력합니다.

```text
필터 A (3줄 입력, 공백 구분)
0 1 0
1 1 1
0 1 0

필터 B (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1

패턴 (3줄 입력, 공백 구분)
1 0 1
0 1 0
1 0 1
```

행 수·열 수 불일치 또는 비숫자 입력 시 안내 메시지를 출력하고 재입력을 유도합니다.

### 모드 1 보너스 — 자동 생성 패턴

모드 1에서 입력 방식 메뉴를 통해 **자동 생성 패턴**을 선택할 수 있습니다. 내부적으로 [`generate_cross_pattern(3)`](main.py#L284)과 [`generate_x_pattern(3)`](main.py#L298)을 호출해 표준 Cross/X 필터를 자동으로 생성하며, 사용자는 직접 숫자를 입력하지 않고도 전체 흐름을 검증할 수 있습니다.

```text
[입력 방식 선택]
1. 직접 입력
2. 자동 생성 패턴 사용 (Cross / X)
```

### 핵심 정책

- **MAC 연산은 직접 구현**: NumPy/벡터화 미사용. 이중 for-loop으로 정확히 N² 회 곱셈·덧셈 수행 → 시간 복잡도 **O(N²)**.
- **라벨 정규화**: expected 값(`'+'`/`'x'`)과 필터 키(`'cross'`/`'x'`)가 모두 한 표준(`Cross`/`X`)으로 수렴하도록 [`normalize_label`](main.py#L63)을 모든 비교 직전에 적용. 표준 라벨은 항상 대소문자 정확히 `Cross` / `X`.
- **동점 처리(epsilon)**: `EPSILON = 1e-9`로 부동소수점 비교. `abs(cross_score - x_score) < 1e-9`이면 `UNDECIDED`. expected가 `UNDECIDED`가 아닌 한 FAIL로 이어집니다.
- **에러 처리**: 모드 1은 잘못된 입력 시 한국어 안내 메시지를 출력하고 같은 그리드를 처음부터 재입력받습니다. 모드 2는 키 파싱 실패·필터 부재·크기 불일치 어느 것도 프로그램을 중단시키지 않으며, 케이스 단위로 `FAIL`과 `fail_reason`을 기록합니다.
- **보너스 — 1D 메모리 최적화**: [`to_1d`](main.py#L311)로 2D를 행 우선 1D로 변환한 뒤 [`mac_operation_1d`](main.py#L320)로 동일 결과를 산출. 2D 대비 인덱스 접근이 단순해져 평균 시간이 더 낮게 측정됩니다(아래 표 참고). 결과값은 `EPSILON` 이내로 일치하는지 매번 검증합니다.
- **보너스 — 패턴 생성기**: [`generate_cross_pattern(n)`](main.py#L284), [`generate_x_pattern(n)`](main.py#L298)이 임의의 N에 대해 표준 패턴을 만들며, 모드 1 자동 입력과 [`run_memory_optimization_comparison`](main.py#L341)의 3×3 케이스에서 재사용됩니다.

## 3. 결과 리포트

### 모드 2 실측 결과 (총 8 케이스)

```text
총 테스트: 8개
통과: 6개
실패: 2개

실패 케이스:
- size_5_3: 크기 불일치 (필터: 5x5, 입력: 7x7)
- size_13_3: 동점(UNDECIDED)
```

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|--------|-----------:|------:|------|----------|------|
| size_5_1  | 9.0  | 1.0  | Cross     | Cross | PASS |
| size_5_2  | 1.0  | 9.0  | X         | X     | PASS |
| size_13_1 | 25.0 | 1.0  | Cross     | Cross | PASS |
| size_13_2 | 1.0  | 25.0 | X         | X     | PASS |
| size_25_1 | 49.0 | 1.0  | Cross     | Cross | PASS |
| size_25_2 | 1.0  | 49.0 | X         | X     | PASS |
| size_5_3  | —    | —    | (분석 전 차단) | X | **FAIL** |
| size_13_3 | 0.0  | 0.0  | UNDECIDED | X     | **FAIL** |

### FAIL 케이스 원인 분석

미션은 의도적으로 두 종류의 "정상이 아닌 입력"을 데이터에 심어 두었습니다. 두 FAIL은 우연한 버그가 아니라 **검증 정책이 정상 동작했다는 증거**입니다.

1. **`size_5_3` — 스키마/크기 불일치 (관점: 스키마)**
   - 필터는 5×5인데 입력 패턴이 7×7로 들어옵니다. [`validate_grid_size`](main.py#L204)가 행 수와 각 행의 열 수를 모두 확인해 `False`를 반환하고, [`analyze_pattern`](main.py#L214)은 MAC 연산을 시도하지 않은 채 즉시 FAIL을 기록합니다.
   - 핵심은 **프로그램이 중단되지 않고 다음 케이스로 계속 진행한다**는 것입니다. fail_reason에 `"크기 불일치 (필터: 5x5, 입력: 7x7)"`이 남아 디버깅에 활용됩니다.

2. **`size_13_3` — 동점(UNDECIDED) (관점: 비교 정책)**
   - 13×13 패턴이 모두 0이라 Cross 필터·X 필터와의 MAC 점수가 정확히 `0.0`으로 같습니다. [`compare_scores`](main.py#L80)는 `abs(0.0 - 0.0) < 1e-9`로 판정해 `UNDECIDED`를 반환하고, expected가 `X`이므로 [`judge_result`](main.py#L92)가 FAIL을 돌려줍니다.
   - 이는 부동소수점 비교에 epsilon 정책을 적용했기에 검출되는 케이스입니다. 만약 `==`로 비교했다면 같은 결과지만, 미세한 부동소수점 오차가 있는 다른 입력에서는 정책 부재 때문에 무작위로 다른 답이 나올 수 있습니다.

### PASS 6개의 의미 — 라벨 정규화의 일관성

PASS로 잡힌 6개는 단순히 점수 차이가 컸기 때문만이 아닙니다. expected 값이 데이터에 따라 `'+'`, `'cross'`, `'x'`, `'X'` 등 다양한 표기로 들어와도 [`normalize_label`](main.py#L63)이 모두 표준 `Cross`/`X`로 수렴시키고, 필터 키(`cross`/`x`) 역시 같은 함수로 정규화한 뒤 비교하기 때문에 라벨 표기의 사소한 차이가 PASS/FAIL 결과를 흔들지 않습니다. 라벨 정규화가 빠지면 `'+'` 같은 값이 표준 라벨과 매칭되지 않아 멀쩡한 케이스가 FAIL로 떨어집니다.

### FAIL 0이 된다면?

향후 데이터셋에서 FAIL이 0이 된다면, 그것은 **스키마/크기 불일치 케이스와 동점 케이스가 데이터에서 사라졌다는 뜻**입니다. 코드의 검증 경로(`validate_grid_size`, `compare_scores`의 epsilon 분기)는 그대로지만, 그 분기를 트리거할 입력이 없을 뿐입니다. 따라서 FAIL 0은 "검증이 약해졌다"가 아니라 "검증할 비정상 입력이 없어졌다"로 해석해야 합니다(MISSION.md R30).

### 실패 원인의 3가지 분류 (정리)

| 관점 | 정책 | 본 데이터의 사례 |
|------|------|------------------|
| **라벨** | [`normalize_label`](main.py#L63)이 `'+'/'cross'/'x'`를 표준 `Cross`/`X`로 통일 | 본 데이터에는 라벨 불일치 FAIL 없음 (정규화가 PASS 6 모두에서 동작) |
| **스키마** | [`validate_grid_size`](main.py#L204)가 행/열 크기 검증, 실패 시 케이스 단위 FAIL | `size_5_3` (7×7 ≠ 5×5) |
| **비교(epsilon)** | [`compare_scores`](main.py#L80)가 `abs(a-b) < 1e-9` 동점 → `UNDECIDED` | `size_13_3` (Cross=X=0.0) |

## 4. 시간 복잡도 분석 / 성능 표

### 성능 표 (실측, 10회 평균, I/O 제외)

```text
| 크기  | 평균 시간(ms) | 연산 횟수 |
| ----- | ------------- | --------- |
| 3×3   | 0.002         | 9         |
| 5×5   | 0.005         | 25        |
| 13×13 | 0.024         | 169       |
| 25×25 | 0.084         | 625       |
```

### O(N²) 근거 — 코드부터

[`mac_operation`](main.py#L53)의 본문은 다음과 같습니다.

```python
for row in range(n):
    for col in range(n):
        result += grid_a[row][col] * grid_b[row][col]
```

이중 for-loop으로 모든 (row, col) 좌표를 정확히 한 번씩 방문하며, 각 좌표에서 곱셈 1회·덧셈 1회를 수행합니다. 따라서 입력 크기 N에 대해 연산 횟수는 정확히 **N²** 회이고, 시간 복잡도는 **O(N²)** 입니다. 추가적인 재귀나 분기, 캐시도 없으므로 알고리즘 자체에 숨은 비용은 없습니다.

### 측정 데이터로 검증

연산 횟수 비율과 실측 시간 비율을 비교하면 다음과 같습니다 (3×3을 기준 1.0으로 정규화).

| 크기 | 연산 횟수 | 횟수 비율 | 실측 ms | 시간 비율 |
|------|----------:|----------:|--------:|----------:|
| 3×3  | 9         | 1.0       | 0.002   | 1.0       |
| 5×5  | 25        | 2.78      | 0.005   | 2.5       |
| 13×13| 169       | 18.78     | 0.024   | 12.0      |
| 25×25| 625       | 69.44     | 0.084   | 42.0      |

작은 크기에서는 함수 호출 오버헤드가 상대적으로 커서 시간 비율이 연산 횟수 비율보다 작게 나타나지만, 25×25에서는 시간 비율(42×)이 횟수 비율(69×)에 점차 근접합니다. 측정 시간 자체가 마이크로초 수준이라 시스템 노이즈가 그대로 보이며, 그래도 **N이 커질수록 시간이 N²에 비례해 증가**한다는 경향은 분명히 확인됩니다. 정확한 비례 검증이 필요하다면 `measure_mac_time(..., repeat=1000)`처럼 반복 횟수를 늘리면 노이즈가 더 줄어듭니다.

### 측정 방법

- [`measure_mac_time`](main.py#L158)에서 [`time.perf_counter()`](https://docs.python.org/3/library/time.html#time.perf_counter)로 시작·종료 시각을 기록한 뒤, 10회 반복 시간을 10으로 나눠 평균을 구합니다.
- I/O와 메뉴 조작은 측정 구간에 포함되지 않으므로, 순수한 MAC 연산 비용만 표에 반영됩니다.
- 작은 크기일수록 함수 호출 자체의 오버헤드가 결과의 큰 부분을 차지하므로, 절대값을 비교하기보다 **N에 따른 증가 추세**를 보는 것이 의도에 맞는 해석입니다.

### 보너스 — 2D vs 1D 비교 (실측)

같은 입력에 대해 2D 표현과 1D 평탄화 표현으로 각각 MAC을 수행한 결과입니다.

```text
| 크기  | 2D ms     | 1D ms     | 비율(2D/1D) |
| ----- | --------- | --------- | ----------- |
| 3×3   | 0.002     | 0.001     | 1.94        |
| 5×5   | 0.004     | 0.003     | 1.79        |
| 13×13 | 0.024     | 0.014     | 1.73        |
| 25×25 | 0.084     | 0.055     | 1.53        |
```

해석: 모든 크기에서 1D 버전이 2D 버전보다 약 1.5~1.9배 빠르게 측정되었습니다. 두 알고리즘의 연산 횟수는 같지만(`for i in range(n*n)` ≡ `for i,j in n×n`), 1D는 `flat[i]` 한 번의 인덱스 접근으로 끝나는 반면 2D는 `grid[row][col]`처럼 두 단계 인덱스 접근(리스트의 리스트)이 필요해 매 반복마다 추가 오버헤드가 누적됩니다. 시간 복잡도는 O(N²)으로 동일하지만, 상수항이 1D 쪽이 더 작은 셈입니다.

N에 따라 비율이 1.94 → 1.79 → 1.73 → 1.53으로 **단조감소**하는데, 이는 측정 노이즈가 아니라 구조적인 이유가 있습니다. 2D 구현은 안쪽 루프의 N² 비용 외에도 **안쪽 루프를 N번 재진입하는 O(N) 추가 비용**을 갖기 때문입니다. [`mac_operation`](main.py#L53)을 다시 보면

```python
for row in range(n):           # 바깥 루프: N번 반복
    for col in range(n):       # 이 줄의 range(n)은 row가 바뀔 때마다 새로 평가됨
        result += grid_a[row][col] * grid_b[row][col]
```

`row`가 한 번 바뀔 때마다 (a) 안쪽 `range(n)` 객체 재생성, (b) `GET_ITER`로 새 이터레이터 생성, (c) 새 루프 블록 셋업 — 이게 **행마다 1회씩, 총 N회** 발생하는 고정 비용입니다. 반면 [`mac_operation_1d`](main.py#L320)는 단일 루프라 이런 재진입 셋업이 아예 없습니다(`range(n·n)` 1번, `GET_ITER` 1번으로 끝).

이를 시간 모델로 적으면

```text
T_2D ≈ a + b·N + c₂·N²       (b·N = 안쪽 루프 N회 재진입 비용)
T_1D ≈ a + c₁·N²
```

이고 비율은

```text
T_2D / T_1D ≈ (c₂ / c₁) + b / (c₁ · N)
```

즉 **상수 + 1/N 꼬리** 형태라 N이 커질수록 단조감소하며 `c₂/c₁`(순수 인덱싱 비용 비율)로 수렴합니다. 실측 데이터를 `ratio = c + d/N` 형태에 맞춰보면 대략 `c ≈ 1.47`, `d ≈ 1.4`가 나오고, 이 모델이 예측하는 비율은 N=3에서 1.94, N=25에서 1.53으로 실측과 잘 일치합니다.

따라서 본 데이터에서 도출되는 결론은 **"1D가 2D보다 대략 1.5배 빠르며, 이 비율이 N→∞에서의 점근값이고 작은 N에서는 안쪽 루프를 N번 재진입하는 오버헤드(`b·N` 항)가 아직 `N²`에 묻히지 않아 비율이 더 부풀어 보인다"** 입니다. 1D와 2D의 결과값은 매번 epsilon 이내로 일치하는지 검증되고 실측에서도 항상 일치했습니다.
